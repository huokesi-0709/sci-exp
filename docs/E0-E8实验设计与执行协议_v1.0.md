# SC-EA-RAG E0–E8实验设计与执行协议 v1.0

状态：代码与分析入口已建立；E0实物校准、正式Gold数据和第二硬件平台尚未完成。
当前400条数据仍是`development_gold`，只能用于管线演练和开发诊断，不能升级为
Gold Test或论文确认性结果。

## 1. 总体结论

实验问题分成三层，顺序不能交换：

1. **测量是否可信**：E0未通过，所有能耗结论停止。
2. **输入与配置是否异质、风险是否可校准、能耗是否可预测**：E1–E3只使用
   Dev-Train、Dev-Temp和Gold Calibration；不得读取Gold Test结果选模型。
3. **方法是否在同等安全下节能且能跨状态/设备稳定**：E4–E8在设计冻结后执行，
   Gold Test只运行一次。

配置固定为C0/Light、C1/Medium、C2/Full和C3/SafeFallback。C3不是一个更小的
生成模型，而是无生成的确定性安全回退，报告时必须单独列出。

## 2. 数据分区冻结

|论文角色|项目映射|允许用途|禁止用途|
|---|---|---|---|
|Dev-Train|`train`|训练安全风险模型、能耗模型|校准阈值、最终报告|
|Dev-Temp|`valid`|实现选择、特征/模型族比较、热状态探索|最终显著性结论|
|Gold Calibration|`cal_op`|冻结每个风险头和配置的阈值|训练模型|
|Challenge Calibration|`cal_ch`|只检查分布偏移|重新选择阈值|
|Gold Test OP|`test_op`|一次最终操作分布报告|任何调参|
|Gold Test CH|`test_ch`|一次最终挑战分布报告|任何调参|

所有分区按`source_group_id`隔离。当前400条虽然文件名含这些分区，但角色仍是
`development_gold`，因此只相当于Dev数据。

## 3. E0 功率测量链验证

**问题**：INA226、采集时钟和查询边界能否支持论文级单查询能耗积分？

必须完成：

- `ZERO`零偏；在可信参考仪器下用中间稳定点执行`CAL`；0.5A/1A/2A各采集至少
  30秒，电压、电流、功率相对误差均不超过2%；
- 三段以上、每段至少60秒的Radxa空闲基线，报告均值、SD、CV和段间漂移；
- 连续60分钟稳定性采集，目标100Hz，最大间隔30ms，丢样率低于0.1%，无序列
  回退、饱和、欠压或integration gap；
- 至少100次查询标记RTT，报告P50/P95/P99；至少10个SYNC回包；
- 冷机和热稳态各复核一次零偏/增益，不继承旧ESP32校准值；
- 记录R010名义值、模块/参考仪器编号、5V负载侧电压和接线照片。

分析入口：`scripts/验证INA226三点校准.py`和`scripts/分析E0功率测量链.py`。
主要证据：三点误差、idle SD、effective Hz、P99 gap、dropout、同步RTT和质量标志。

## 4. E1 配置异质性

**问题**：如果所有输入的最低能耗安全配置都相同，Router就没有存在必要。

在Dev-Train/Dev-Temp对每个query穷举C0/C1/C2，至少3次重复，顺序用固定seed随机化。
每个输出完成盲法双审和仲裁；每次运行必须具有有效物理能耗。对每个query定义：

`safe(c)=not y_trigger and not y_miss and y_quality`

Oracle在真实安全集合中选择实测能耗最低配置；没有安全配置时选择C3。报告：

- Oracle配置占比和熵；
- 各query安全配置集合矩阵；
- C0/C1/C2安全率—能耗Pareto；
- Oracle是否实际使用多个配置。

若Oracle几乎恒定选择同一配置，异质路由贡献不成立。入口：
`scripts/分析E1配置异质性.py`。

## 5. E2 Safety calibration

**问题**：风险分数和阈值能否控制不安全接受，而不是只提高平均准确率？

训练只用Dev-Train，模型选择只用Dev-Temp，阈值只用Gold Calibration。风险头为
`trigger`、`miss`、`quality_failure`及其combined risk。每个头和配置报告：

- AUPRC（不平衡标签的主判别指标）；
- Recall、Brier、10-bin ECE；
- UAR = unsafe accepted / all unsafe；
- SER = unsafe accepted / all accepted；
- 接受率与C3回退率。

Gold Test只评估已冻结模型和阈值。入口：`scripts/分析E2安全校准.py`。

## 6. E3 能耗预测与Static Energy Table强基线

**问题**：查询级和硬件状态级能耗预测是否真的优于查平均成本表？

必须在相同安全可行集合下比较：

1. `Static Mean Energy`：每个配置在Dev-Train的平均物理能耗；
2. `No-State Predictor`：查询表面特征＋配置，不读取硬件状态；
3. `State-Aware Predictor`：上述特征加Radxa SoC温度、可用内存、load、CPU频率、
   cooling state；SHT31温湿度只作环境协变量，不能冒充device temperature。

独立测试报告MAE、MdAE、RMSE、MAPE（仅实际能耗≥0.1J）、配置内Spearman、
energy regret以及10J/5J/3J预算违反率。只有state-aware同时优于static和no-state，
才能把hardware-aware energy selection作为核心贡献；否则降级为鲁棒性或负结果。

训练/评估入口：`scripts/分析E3能耗预测.py`。模型保存在
`models/energy/energy_{static_mean,no_state,state_aware}.joblib`。配置生成入口：
`scripts/生成E3路由配置.py`。

## 7. E4 主实验

**问题**：在相同安全标准下，SC-EA-RAG是否降低端到端物理能耗？

至少比较：

- Fixed-Light、Fixed-Medium、Fixed-Full；
- Soft Weighting（安全风险和能耗软加权，无硬安全保证）；
- Safety Router + Static Mean Energy（强closest baseline）；
- Safety Router + No-State Predictor；
- SC-EA-RAG + State-Aware Predictor；
- 真实标签和实测能耗构造的Oracle（仅为上界，不可部署）。

所有方法共用同一生成模型、配置库、token上限、协议库和检索器。查询顺序随机化，
每配置/方法先做3次不计入统计的预热，正式至少3次。查询标记从路由前开始，到生成
结束后停止，因此E2E能耗已经包含Router成本。

报告Safety–Energy Pareto、均值/中位数/P95能耗、时延、C3率、配置分布和失败/OOM。
入口：`scripts/分析E4主实验.py`。

## 8. E5 Router overhead

**问题**：Router成本是否吞掉节能收益？

执行两种测量：

- 纯Router批量microbenchmark，避免每次UDP标记开销主导结果；整个批次只标记一次，
  批次物理能耗除以调用次数；
- E4完整E2E物理能耗。

记`baseline`为固定基线，`method_E2E`已含Router：

- gross saving = baseline − (method_E2E − router cost)
- net saving = baseline − method_E2E

Router成本不能从E2E结果中重复扣除。入口：`scripts/基准测试E5Router开销.py`和
`scripts/分析E5净节能.py`。

## 9. E6 Hardware-state stress

### 9.1 温度

先记录Radxa SoC温度、CPU frequency和cooling state，主动预热探索设备实际热行为；
在看到频率/冷却状态转折后才冻结`low stable / near-limit / throttled`三个区间，不预写
45/65/80°C。SHT31只报告ambient temperature/humidity。正式查询测量前停止预热负载，
不得把预热能耗算进查询。如果状态不改变配置可行性或成本排序，thermal-aware只能写
robustness。

### 9.2 内存

使用`scripts/保持低CPU内存占用.py`分配并保持内存页，构造High/Medium/Low available
memory headroom。它比高CPU的`stress-ng`更干净。每个档位先确认没有swap thrashing，
再测C0/C1/C2峰值内存、OOM/失败和路由规避率。

### 9.3 可用能源预算

没有fuel gauge时只称`available energy budget`，通过`SCI_EXP_ENERGY_BUDGET_J=10/5/3`
设置，不声称电池剩余15%。报告配置热图、C3率和实际预算违反率。

状态记录入口：`scripts/记录Radxa硬件状态.py`；分析入口：
`scripts/分析E6硬件状态压力.py`。

## 10. E7 第二硬件平台

在第二边缘设备复用配置语义、协议库和安全评估，但重新采集静态成本表、训练/校验
能耗模型、检查安全阈值适用性。不能把Radxa资源画像直接复制过去。若项目周期内没有
第二平台，删除“跨硬件泛化”主张，不用模拟设备代替。入口：`scripts/分析E7跨设备.py`。

## 11. E8 统计与稳定性

- 固定seed随机化运行顺序，保留`run_order`；
- 至少3次独立重复，报告mean、SD、median、P95；
- 以query为重采样单位做10,000次配对bootstrap，避免把同一query的重复当成独立样本；
- 报告方法相对强closest baseline的能耗差和安全率差95% CI；
- 失败、超时、OOM和无效功率运行不删除，分别报告ITT式失败率和有效物理测量子集。

入口：`scripts/分析E8统计稳定性.py`。

## 12. 执行顺序与停止规则

严格顺序：E0 → Dev smoke/真实小先导 → E1 → E2训练与Gold Calibration → E3 →
冻结方法和阈值 → E4/E5/E6 → 单次Gold Test → E8 → 可选E7。

出现以下任一情况立即停止论文级运行：E0失败、分区泄漏、盲审不完整、能耗记录
`external_meter_valid!=true`、Gold Test仍是development gold、或测试结果被用于模型/阈值
选择。
