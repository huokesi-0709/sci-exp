# 预处理数据泄漏与原始信号审查

## 1. 审查结论

审查对象包括：

- 查询预处理、异常隔离和增强；
- 400条开发查询的构建、双审与六分区；
- 推理特征、C1/C2检索、风险模型和校准；
- 协议抽取与切块；
- Radxa运行日志和资源画像；
- 当前研究协议与质量门禁。

总体结论：

> 当前项目的工程质量门禁较完整，400条数据也已经被正确降级为
> `development_gold_not_confirmatory_3600`。但是，在构建最终3,600条确认性数据
> 和启动正式Radxa实验前，仍有两项P0阻断问题和多项P1风险必须处理。否则，结果
> 可能被金标准元数据、模板痕迹或伪重复抬高，无法代表真实逐查询配置选择能力。

P0阻断项：

1. C2检索直接读取人工标注的`disaster_type`；
2. 新增304条的“双审者”标签由脚本按固定序号制造差异，不是两名独立审查者的真实标注。

当前400条可以继续用于代码调试、错误发现和训练集先导实验，但不得进入最终
`cal_op`、`cal_ch`、`test_op`或`test_ch`。这一边界已经在
`研究协议_v2.0_确认性设计冻结.md`中正确写明。

## 2. 已经做得较稳健的部分

以下控制真实存在，并非只写在文档中：

- `query_features()`只使用查询时可从文本表面获得的特征；
- 风险模型特征已排除`risk_level`、`query_type`、`should_fallback`、
  `disaster_type`和`gold_evidence_ids`；
- 单元测试检查推理特征不含上述gold字段；
- 同一`source_group_id`不跨分区；
- 近重复阻断簇不跨分区；
- 增强仅允许出现在train；
- 400条被明确标为开发gold，不是最终确认性测试；
- 外部公开数据审计正确识别了单一来源集中、没有封存测试集的问题；
- 资源异常值默认只标记、不静默删除；
- 数据文件、模型和分区具有SHA-256留痕；
- 52项现有单元测试全部通过。

这些控制应保留，但现有测试通过并不代表没有系统级标签泄漏。

## 4. 详细问题与证据

### R1：人工灾种标签进入正式C2检索

位置：

- `src/sci_exp/pipelines.py:101-143`
- `src/sci_exp/retrieval.py:233-240`

C2执行以下操作：

1. 用`query.disaster_type`严格过滤候选协议；
2. 用`query.disaster_type`构建第二步扩展查询；
3. 用`query.disaster_type`给重排结果增加灾种匹配分。

但`disaster_type`来自人工gold查询记录，不是当前系统从用户输入实时预测的字段。
因此，虽然风险模型本身没有读取gold灾种，完整RAG系统仍获得了一个真实部署时
不存在的“完美灾种分类器”。

本次审查做了实际对照：

```text
查询文本：现在应该怎么办？
其他字段完全相同
```

只把`disaster_type`从`fire`改成`poisoning`，C2检索结果便从火灾协议集合切换成
中毒协议集合，证明该字段会实质改变输出。

现有`test_gold_labels_do_not_change_retrieval`只改变`gold_evidence_ids`，没有改变
`disaster_type`，因此没有捕获此问题。

稳健替代：

- 把查询对象拆成`InferenceQuery`和`GoldLabels`；
- `InferenceQuery`只包含原始文本及真实用户已经提供的地区、时间等字段；
- C1、C2和路由器的函数签名只能接收`InferenceQuery`；
- 灾种由冻结的train-only文本分类器预测，或从初次检索候选分布推断；
- 预测灾种必须保存概率和`unknown`状态；
- 不确定时进行多灾种检索或C3回退，不能使用gold灾种；
- 新增不变性测试：同一文本改变所有gold字段，RAG输出必须完全不变。

### R2：新增304条不是真实独立双审

位置：

- `scripts/构建400条正式查询集并双审.py:421-432`
- `scripts/构建400条正式查询集并双审.py:463-497`

脚本先把A、B两人的风险和回退标签都设为场景预设值，然后：

- 当`serial % 29 == 0`时修改B的风险等级；
- 当`serial % 23 == 0`时反转B的回退标签。

因此，报告中的：

```text
risk_cohen_kappa = 0.971243
fallback_cohen_kappa = 0.890968
```

是由预设标签和固定序号翻转产生的模拟一致性，不是两名审查者独立阅读查询后得到
的经验一致性。把它描述为“正式双审”会高估标注可信度。

稳健替代：

1. 查询构建者不担任两位正式标注者中的任何一位，或至少不得同时兼任仲裁者；
2. A、B分别获得不含对方结果、不含预设风险/回退值的工作单；
3. 两人独立提交带时间戳的原始标注文件；
4. 一致性统计只能从这两个原始文件计算；
5. 仲裁者只查看真实分歧项；
6. 永久保留A、B和仲裁三个版本，不覆盖；
7. 当前304条的A/B字段改名为`simulated_review_for_pipeline_test`，不得再作为真实双审证据。

### R3：短查询是否保留依赖gold标签

位置：

- `src/sci_exp/preprocessing.py:269-339`

当查询少于`min_characters`时，代码把`risk_level`和`should_fallback`传给
`_is_meaningful_short_query()`。只有风险不低或应回退且包含特定字符的短查询才被
保留。

这不是把标签直接喂给模型，但它用结局标签决定样本能否进入数据集，会造成
label-dependent selection：

- 高风险短查询更容易保留；
- 低风险短查询更容易被隔离；
- 短查询挑战集的风险比例被人为改变；
- 模型评价不能反映真实短输入分布。

稳健替代：

- 样本保留规则只能读取`raw_text`、编码状态和来源许可；
- 所有2字符及以上短查询先进入`short_query_review`；
- 由不知道gold风险的人员判断是否为有效语言输入；
- `risk_level`和`should_fallback`在纳入决定冻结后才标注；
- 无法判定的短查询保留在独立挑战集，不因标签删除。

### R4：模板后缀泄露风险标签

位置：

- `scripts/构建400条正式查询集并双审.py:195-204`
- `scripts/构建400条正式查询集并双审.py:207-275`
- `scripts/构建400条正式查询集并双审.py:361-366`

新增304条由两条场景陈述循环配合八个固定后缀生成。L3场景每组只生成6条，其他
场景通常生成7或8条，导致后缀索引与标签相关。

实测结果：

| 后缀 | 数量 | L3数量 |
|---|---:|---:|
| 现在应该先做什么 | 39 | 16 |
| 请给我最先执行的两步 | 39 | 16 |
| 手机网络很差，我该怎么处理 | 39 | 16 |
| 现场只有普通人能帮忙，先做什么 | 39 | 16 |
| 请按紧急程度告诉我行动顺序 | 39 | 16 |
| 救援还没到，哪些事绝对不能做 | 39 | 16 |
| 我需要一段简短、可离线执行的指引 | 23 | 0 |
| 如果情况继续恶化，什么时候必须求救 | 20 | 0 |

最后两个后缀成为“非L3”捷径。即便模型看不到`risk_level`，也可以从文本模板猜到
标签。

稳健替代：

- 最终确认性运营集优先使用自然或准自然查询，不使用固定后缀扩写；
- 必须使用模板时，采用标签平衡的完整交叉设计；
- 每个后缀在每个风险等级、回退类别和灾种中出现次数接近；
- 将`template_family_id`纳入分组，模板家族不能跨train/cal/test；
- 训练一个“只看后缀”的探针模型；若明显高于多数类基线，阻断冻结；
- 删除模板提示语后重新评估，结论应基本不变。

### R5：协议反向编写查询造成词汇捷径

304条记录的`data_origin`为
`researcher_authored_protocol_grounded_scenario`。查询、gold evidence、必需行动
和禁止行动在同一个脚本中同时定义。

这会产生：

- 查询措辞与协议措辞过度相似；
- 检索Recall@k虚高；
- 证据绑定边界过于清晰；
- 风险模型学习研究者语言风格，而不是自然应急表达。

稳健替代：

- 查询收集或编写与证据绑定分离；
- 查询编写者只看到场景概要，不看到目标协议原句；
- gold证据由另一组人员在查询冻结后绑定；
- 运营测试集以公开自然文本或独立人员编写文本为主；
- 研究者协议派生文本只进入train和挑战集；
- 报告自然查询、协议派生查询和模板查询三种来源的分层结果。

### R6：分区算法使用全部gold标签

位置：

- `scripts/按场景分层冻结正式400条.py:401-429`
- `scripts/按场景分层冻结正式400条.py:432-629`

当前开发分区使用：

- `risk_level`；
- `should_fallback`；
- `query_type`；
- `disaster_type`；
- gold证据来源。

来保证各分区的配额和平衡。

对400条开发集而言，这种做法可以用于确保工程覆盖；但对最终确认性数据，如果
研究团队查看全部gold后反复优化`test_op`分布，就会形成测试设计过拟合。

稳健替代：

1. 先按来源、事件、时间、地区、模板家族和采集批次定义分区单元；
2. 使用不含gold结局的来源层变量分配运营分区；
3. 冻结并哈希`query_id → split`映射；
4. 再进行风险、回退和证据标注；
5. 标签揭盲后只检查是否达到最低可分析数量，不重新移动样本；
6. 若某类不足，新增独立来源批次，不能从测试集搬运；
7. 风险富集样本进入`test_ch`，不能混入用于估计自然风险的`test_op`。

### R7：空列表混淆“没有”和“未标注”

位置：

- `src/sci_exp/preprocessing.py:255-261`
- `src/sci_exp/preprocessing.py:303-310`

当`gold_evidence_ids`、`required_actions`或`prohibited_actions`缺失/为null时，
当前流程转为空列表并记录警告。这样无法区分：

- 审查者已经确认没有适用项；
- 字段尚未标注；
- 数据导入丢失；
- 场景本来属于证据缺口。

在评价中，空`required_actions`会使完整率变成`None`，空gold evidence会使检索
召回变成`None`，可能让困难样本悄悄退出统计。

稳健替代：

- 保留`null`表示未标注；
- `[]`只表示审查后确认无适用项；
- 增加`evidence_annotation_status`、`action_annotation_status`；
- 正式train/cal/test要求状态为`adjudicated`；
- 只有预定义`out_of_scope`或`designed_evidence_gap`允许空gold证据；
- 正式模式下缺失不应仅警告，应阻断。

### R8：正式风险训练可能退回smoke标签

位置：

- `src/sci_exp/risk_model.py:38-44`
- `src/sci_exp/risk_model.py:165-176`

代码使用：

```python
metrics = row.get("adjudication", row.get("metrics"))
```

如果没有`adjudication`，便使用运行器的smoke启发式`metrics`。当前
`train_calibrate_route.sh`先调用人工标签合并，能降低误用概率，但底层CLI仍允许
直接把启发式标签训练成“正式风险模型”。

稳健替代：

- 增加`--mode formal|smoke`；
- formal模式必须存在`adjudication`且标签版本已冻结；
- formal模式发现`metric_scope=smoke_heuristic_not_publication_grade`立即失败；
- 模型文件写入标签文件哈希、标注手册版本和分区哈希；
- 校准同样只接受正式仲裁标签。

### R9：固定字符切块可能破坏协议原始结构

位置：

- `src/sci_exp/ingestion.py:48-89`

当前切块以600字符和80字符重叠为主，优先寻找段落或句末。这对普通段落可用，但
可能破坏：

- 编号步骤及其前置条件；
- 表格行列关系；
- “适用/不适用”标题与正文关系；
- 跨页否定句；
- 剂量、单位和脚注；
- 同一段被重叠复制后造成检索证据重复计数。

稳健替代：

- 保存`raw_text`、页码、章节路径和源定位；
- 先按标题、列表、表格和步骤解析，再在结构单元内切块；
- “禁止/不得/仅当/除非”等约束与其动作保持同块；
- 表格转换为带列名的逐行记录；
- 重叠块携带`parent_section_id`，评价时按父段去重；
- 对每个协议抽检步骤完整率、否定保持率、表格保持率和页码可追溯率。

### R10：资源画像存在幸存者偏倚

位置：

- `src/sci_exp/resource_model.py:10-47`

资源画像只纳入`status == "ok"`的运行。超时、OOM、服务崩溃和空输出被排除后，
高成本配置的时延和能耗可能看起来更低。

稳健替代：

- 失败运行保留在到达查询分母中；
- 超时按预注册上限作为删失/惩罚值；
- OOM单独报告，不进入“可部署”集合；
- 资源主结果按查询配对比较C0–C3；
- 同时报告成功条件资源和到达查询总体资源；
- 模型使用查询长度、输出token、冷热态和设备状态，而非每配置一个常数中位数。

### R11：资源预处理没有接入正式闭环

位置：

- `scripts/train_calibrate_route.sh`

项目有`preprocess-runs`命令，但正式脚本直接把
`results/radxa_train_runs.jsonl`交给`profile-resources`，没有先执行缺失检查、
异常标记和质量门禁。

稳健替代顺序：

```text
radxa_train_runs.raw.jsonl
→ preprocess-runs
→ radxa_train_runs.cleaned.jsonl
→ 人工确认隔离/设备故障
→ profile-resources
```

原始日志必须保留，cleaned文件和人工排除决定分别留痕。

### R12：重复运行可能是质量伪重复

配置设置`repetitions=3`和`temperature=0.0`，但发送给`llama-server`的payload没有
seed。三次运行可能生成完全相同回答。

这三次适合测量设备时延/能耗变异，但不能自动视为三个独立输出质量样本。

稳健替代：

- 资源重复：固定输出/seed，测量5次以上，按设备会话分析；
- 质量重复：显式传入预注册`generation_seed`，并确认输出确有变化；
- 若temperature=0且输出完全相同，质量结局按一个查询—配置输出计数；
- 人工标签应逐输出绑定`run_key`，不能用一个generic标签复制到不同输出。

### R13：时间外和地区外的命名强于实际隔离

`test_ch`把2026协议家族和晋城地区协议家族留出训练查询，但这些协议块仍进入
完整RAG知识库。因此这更接近：

> 路由器未见过该查询/协议家族，但部署知识库中已经包含该协议。

它不是：

> 系统在完全未见未来或地区协议内容的情况下外推。

稳健替代：

- 将当前子集改名为“未见查询家族、知识库可用”；
- 另建严格测试：训练/开发阶段知识库不含新协议，部署更新阶段再注入；
- 分别报告`KB-known/query-unseen`和`KB-unseen`。

### R14：规范化结果覆盖原始文本

当前规范化把NFKC、零宽字符删除和空白处理后的文本写回`text`。原始信号仍存在于
raw文件，但单条processed记录中无法直接对照。

可能损失：

- 全角/半角、特殊单位和兼容字符；
- 多行结构；
- 重复空格和输入法痕迹；
- 一部分可用于噪声鲁棒性研究的原始形式。

稳健替代：

```json
{
  "raw_text": "原始输入",
  "normalized_text": "模型输入",
  "normalization_steps": ["NFKC", "zero_width_removed"],
  "raw_text_sha256": "..."
}
```

模型默认使用`normalized_text`，挑战实验可以使用`raw_text`，评价和审计可复核差异。

### R15：敏感信息隔离会改变样本分布

当前研究协议明确不纳入可识别信息，因此PII命中后隔离是合适的伦理控制。但若未来
研究真实应急查询，直接删除所有含位置、电话或机构的记录会系统性排除更真实、更
具体的求助文本。

未来替代：

- 先在受限区去标识；
- 用`[PHONE]`、`[LOCATION]`等类型占位符保留句法；
- 由数据管理员确认不可重识别后再纳入；
- 记录去标识前后长度和类型；
- 真实数据研究必须另行伦理审批。

### R16：标点增强可能改变模型直接特征

训练增强会添加/替换问号，而风险模型包含`has_question_mark`和
`character_count`。因此增强并非对当前模型完全“标签保持”的无害变换，还可能
改变样本权重。

当前默认增强数为0，这一点是安全的。

若未来启用：

- 使用父样本权重，使一个父样本的总权重为1；
- 训练中随机增强，而不是永久复制；
- 做模型对标点变化的不变性测试；
- 主结果必须包含不增强版本；
- 增强样本不计入有效独立样本量。

### R17：布尔字符串解析风险

位置：

- `src/sci_exp/schemas.py:121`

Python中`bool("false")`为`True`。虽然预处理器要求原值必须是真布尔值，但其他
代码可以绕过预处理直接加载JSONL。

稳健替代：

- 只接受JSON布尔`true/false`；
- 字符串值一律报错；
- 所有正式入口先过同一个严格schema；
- 禁止配置文件直接指向未经预处理的raw查询。

## 5. 更稳健的替代流程

### 阶段A：分离数据平面

建立三张逻辑表：

1. `inference_queries.jsonl`：系统在决策时真正可见的字段；
2. `gold_labels.jsonl`：风险、回退、gold证据和行动标签；
3. `provenance.jsonl`：来源、事件、模板、协议家族和审计信息。

正式推理代码只能读取第1张表。评价程序在输出生成后按`query_id`连接第2张表。
分区程序使用第3张表中的来源字段，不使用gold结局。

### 阶段B：先采样和分组，后标注结局

```text
自然/准自然查询池
→ 许可与PII门禁
→ 原文去重和近重复聚类
→ 事件/来源/模板/时间/地区分组
→ 冻结split映射
→ 双盲gold标注
→ 标签揭盲后的只读质量审计
```

如果标签揭盲后数量不足，新增独立采集批次，不移动既有测试样本。

### 阶段C：查询预处理

- 原始文本不可变；
- 规范化文本单独保存；
- 纳入/隔离规则不得读取gold标签；
- “未标注”与“确认无”分开；
- 短查询、噪声、方言和错别字优先标为挑战属性，不自动删除；
- 仅train拟合词表、尺度、类别权重和任何数据驱动阈值。

### 阶段D：真实独立标注

- A/B独立工作单；
- 不显示预设标签和对方答案；
- 查询gold标注和系统输出标注分开；
- 仲裁只处理分歧；
- 一致性只由原始A/B结果计算；
- 每个输出标签绑定`query_id + configuration + generation_seed + repetition`。

### 阶段E：知识库预处理

- 结构化抽取标题、列表、表格、步骤和页码；
- 保存源定位和父段ID；
- 切块规则只在train/开发阶段调整；
- 确认性测试开始前冻结协议库；
- 时间/地区外实验明确区分协议是否存在于知识库。

### 阶段F：推理字段白名单

部署允许字段建议为：

```text
query_id
raw_text / normalized_text
用户明确提供的粗粒度地区
系统当前日期
用户明确提供的对象/环境信息
实时设备内存、温度、电量和负载
```

禁止字段：

```text
risk_level
should_fallback
gold_evidence_ids
required_actions
prohibited_actions
人工query_type
人工disaster_type
split_assignment_reason
challenge_flags
未来结果或人工评分
```

如需要灾种，必须使用冻结的预测器输出，不能读取人工gold。

### 阶段G：Windows与Radxa职责

Windows完成：

- 原始数据登记、去标识和结构化；
- 分组、冻结和真实双审；
- train-only预处理和风险模型训练；
- 协议结构化切块；
- 数据、模型、配置和split哈希。

Radxa只接收：

- 冻结的`inference_queries`；
- 独立保存但不提供给推理代码的评价ID清单；
- 冻结协议库；
- 冻结模型和配置。

Radxa完成：

- C0–C3配对运行；
- 物理能耗、时延、内存和温度测量；
- 原始运行日志和设备事件记录。

gold标签不需要提供给生成、检索或路由进程。可在结果复制回Windows后离线连接。

### 阶段H：资源日志

```text
原始设备日志
→ run_key完整性
→ 外部功率计时间对齐
→ 缺失和失败分类
→ 按查询/配置/会话的异常标记
→ 人工设备故障裁决
→ 成功条件与到达查询两套统计
→ 资源预测模型
```

异常值检测必须控制查询长度、输出token和冷热态，不能只在配置内用一个总体MAD。

### 阶段I：校准与测试封存

- train：拟合模型和尺度；
- valid：超参数与checkpoint；
- cal_op：主阈值；
- cal_ch：挑战诊断，不调整主阈值；
- test_op：所有规则冻结后只运行一次；
- test_ch：单独报告；
- 400条开发gold最多进入最终train，不能进入最终cal/test；
- `delta_total=0.05`按三个生成配置分配，正式脚本不得仍使用未调整的0.05。

## 7. 正式实验前必须新增的自动检查

- [ ] 相同文本改变所有gold字段，路由和RAG结果完全不变；
- [ ] C2不直接读取人工`disaster_type`；
- [ ] 正式推理输入不存在gold字段；
- [ ] 短查询纳入决定不读取风险或回退标签；
- [ ] 缺失gold字段不会自动转为空并进入正式数据；
- [ ] template-only探针不能显著预测L3/C3；
- [ ] 模板家族、事件簇、来源记录和扰动父样本不跨分区；
- [ ] 真实A/B文件存在，且一致性不是脚本构造；
- [ ] formal风险训练拒绝smoke标签；
- [ ] 协议切块保持否定、步骤和源定位；
- [ ] `preprocess-runs`已经接入资源画像前；
- [ ] 超时/OOM不会从资源分母中消失；
- [ ] generation seed实际发送给本地模型；
- [ ] 质量重复和设备重复分别计数；
- [ ] 正式Radxa进程无法读取gold目录；
- [ ] 400条开发gold没有进入最终cal/test；
- [ ] 最终test映射在标注和方法优化前封存。

## 8. 建议修复顺序

### 第一批：立即修复，阻断确认性实验

1. 拆分推理字段与gold字段；
2. 移除C2对人工`disaster_type`的访问；
3. 将304条脚本模拟双审降级为工程测试，重新进行真实双审；
4. 移除短查询纳入对gold标签的依赖；
5. 正式训练强制只接受人工仲裁标签。

### 第二批：构建3,600条前修复

1. 先来源分组和封存，再标注；
2. 建立独立自然/准自然运营数据来源；
3. 消除模板后缀与标签相关；
4. 区分未标注和确认无；
5. 引入结构化协议切块和父段去重。

### 第三批：Radxa正式运行前修复

1. 接入资源日志预处理；
2. 将失败运行纳入总体资源和安全结局；
3. 分离质量seed与资源重复；
4. 发送真实generation seed；
5. 修正多配置校准的`delta`分配；
6. 重新运行完整测试和字段白名单审计。

## 9. 对当前数据的处置建议

| 数据 | 建议角色 |
|---|---|
| 400条开发gold | 工程开发、错误分析、可计入最终train |
| 当前400条cal/test分区 | 仅开发期内部验证，不是确认性cal/test |
| 304条脚本生成A/B标注 | 管线测试记录，不作为真实双审证据 |
| 96条历史扩展 | 仅在确认真实独立标注来源后决定是否进入train |
| 307条CrisisNLP文本 | 外部适应/自然语言风格参考；不能作为协议安全gold |
| 当前时间外/地区外子集 | `KB-known/query-family-unseen`探索性挑战 |
| smoke启发式指标 | 代码验证，不进入正式风险训练或校准 |

最终判断：

> 项目已经具备较好的数据工程骨架，但还不能把“所有质量门禁通过”等同于“没有
> 泄漏”。当前最严重的不是随机划分重复，而是gold灾种通过C2检索链路进入系统，
> 以及脚本生成的双审一致性被当成真实标注证据。修复这两项后，再构建最终3,600条
> 数据，才能让Radxa实验证明真实的离线逐查询配置选择能力。
