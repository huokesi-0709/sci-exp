# 正式双盲标注 SOP

## 1. 启动条件

正式标注前必须全部满足：

- 查询、`source_group_id` 和候选用途已冻结；
- 语料、手册、风险/动作/约束本体已由 C 审核；
- A/B 已通过独立试标；
- A/B 使用互不可见的账号、目录或文件；
- 已确定伦理审批、豁免或不适用状态；
- 正式批次不含训练题和试标题；
- P 已生成批次 manifest 和输入哈希。

任一条件不满足，批次状态保持 `blocked_before_annotation`。

## 2. 盲法设计

A/B 可以看到：

- `query_id`、查询文本和合法可观察背景；
- 冻结协议语料和来源卡；
- 当前手册和本体；
- 标注工具的字段说明。

A/B 不得看到：

- 对方原始标签；
- 旧开发标签和脚本模拟标签；
- 模型输出、配置、风险分数、检索排名和能耗；
- Gold Test 的总体标签分布；
- 为达到配额而期望他们选择的类别。

P 应为 A/B 生成不同随机顺序。query ID 保持不变，以便统计配对。

## 3. 批次管理

建议每批 30–50 条。文件名示例：

```text
formal/reviewer_A/IG-A-BATCH001-v1.0.csv
formal/reviewer_B/IG-B-BATCH001-v1.0.csv
```

每一批均记录：

- blind batch ID；
- 查询文件和协议语料 SHA-256；
- 手册、本体和 Schema 版本；
- A/B 分配时间和截止时间；
- 提交时间和文件哈希；
- 任何中断、咨询和版本偏离。

正式标注过程中不得修改手册。如发现阻断性定义错误，暂停整个批次，登记异常，发布新版本
后用新批次 ID 重新开始。

## 4. 标注者操作

对每条记录：

1. 完整阅读查询和 observable context；
2. 标记查询明确事实、否定和缺失条件；
3. 按手册顺序完成全部字段；
4. 打开完整证据切块，而不是只看检索摘要；
5. 用 rationale 记录边界和证据依据；
6. 执行 required/prohibited、critical subset 等自检；
7. 保存但不与另一名标注者讨论。

标注者遇到本体缺项时，只能使用 `ONTOLOGY_GAP` 和约定的 REVIEW 占位 ID；不得自行增加
正式 ID。P 收集问题，但在本批次锁定前不得透露另一人的处理方式。

## 5. 提交和锁定

1. A/B 分别提交给 P；
2. P 立即复制到受控位置并计算 SHA-256；
3. P 运行 Schema、重复 ID、字段范围和集合冲突检查；
4. 结构错误由原标注者修复，形成新文件版本并保留旧文件；
5. 内容判断不得在看到一致性结果后回改；
6. 结构校验通过后状态变为 `raw_labels_locked`。

## 6. 正式一致性和仲裁顺序

```text
A/B raw_labels_locked
→ P 计算仲裁前一致性
→ 保存完整报告和分歧清单
→ C 仲裁全部内容分歧
→ C 复核全部 S3、升级冲突和 evidence gap
→ P 执行最终质量门禁
→ S 批准用途和冻结
```

不得先仲裁再计算 A/B 一致性。

## 7. 防止测试集泄漏

- Gold Calibration 和 Gold Test 使用互斥 `source_group_id`；
- P 在标签之前按来源、事件、模板、地区和时间冻结分区，不能按标签结果重新分配；
- A/B 不需要知道具体是 Calibration 还是 Test；
- 推理设备不得接收本目录；
- Gold Test 只有在方法、阈值和分析计划冻结后才允许用于一次最终评估。
