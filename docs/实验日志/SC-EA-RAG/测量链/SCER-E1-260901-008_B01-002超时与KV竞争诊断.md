`E1-DEVTEMP-FORMAL-B01-002`按冻结顺序完整尝试global run order 1–63，但runner仅48次成功、
15次失败，CLI按设计返回exit code 3。失败包括13次`llama-server request failed: timed out`和
2次HTTP 500；配置分布为C2 14次、C1 1次。该尝试不能生成要求315条全部成功且物理有效的盲审包，

## runner与服务诊断

runner文件为`results/E1_devtemp_formal_v1_B01_attempt002.jsonl`，共63行；当前Windows日志登记时
尚待从Radxa补录字节数和SHA-256。runner汇总为`successful=48`、`failed=15`。

冻结v1配置使用180秒HTTP超时。服务启动时未固定parallel，因此自动得到`n_parallel=4`及
`kv_unified=true`，而实验runner本身是串行请求。服务日志显示：

- 多条C2请求接近180秒后由客户端超时并触发`cancel task`；
- 随后任务出现大量`failed to find free space in the KV cache`与缩小batch重试；
- 两个HTTP 500对应`Context size has been exceeded`；
- 服务在批次结束后仍保持`/health={"status":"ok"}`，不支持进程整体崩溃解释。

综合证据表明，180秒超时使长C2请求被取消并与后续请求在四个slot中短暂交叠，造成统一KV竞争和
级联500。这是正式运行基础设施参数缺陷，不是应当解释为C2方法本身不可行的受控超时结果。

## 版本化修复

不修改旧`configs/E1_devtemp_v1.json`。新增`configs/E1_devtemp_v2.json`：生成、检索、token和上下文
语义保持不变，只把HTTP超时从180秒提高到300秒，并使用新的默认输出名。正式运行服务改为
`--parallel 1`，与串行runner一致；继续保持`--ctx-size 4096 --no-cache-prompt --cache-ram 0
--no-cache-idle-slots`。修订清单见`configs/E1_runtime_revision_v2_20260901.json`。

HTTP 500处理同时改为保留最多2,000字符的服务响应正文，后续若再次失败可直接看到服务端原因。

## 自动停止采集器

Windows采集器新增显式参数`--stop-on-marker-event collector_stop`；runner新增
`--stop-collector-on-exit`。runner无论返回0、2、3或抛出异常，都会最多重试3次发送停止控制并等待ACK。
collector先把`collector_control`写入raw，回传`collector_stopping=true`，再正常关闭串口并打印统计。
控制记录单独计为`control`，不污染实验`marker`计数。

本地COM18端到端非正式smoke已通过：1,622个sample、17个environment、`control=1`，三项invalid均为0，
采集器收到ACK后自行退出。该smoke不属于正式E1证据。
