# 实验对照公平性审查

审查对象：

- `D:\projects\RAG-sci\docs\离线应急RAG_对照实验设计.md`
- `D:\projects\RAG-sci\docs\sci-exp` 当前实验实现

审查结论：

> 对照方案在“同一查询、同一知识库、同一生成模型、独立校准、配对运行和统一
> 安全目标”方面方向正确，但目前仍属于**设计基本合理、尚未达到确认性公平比较
> 条件**。最主要的问题不是某一个基线明显受到偏袒，而是训练预算、预训练资源、
> 调参预算、随机种子和评价口径尚未被锁定；当前代码实现也还没有覆盖纸面定义的
> PROPOSED 和全部基线。

## 1. 总体判定

| 审查维度 | 当前状态 | 不公平风险 | 结论 |
| --- | --- | --- | --- |
| 数据划分 | 已提出同查询、冻结知识库和独立校准 | 缺少统一划分清单、哈希、独立调参验证集和多划分稳健性 | 中高 |
| 训练轮数 | 当前风险模型固定迭代 1200 次 | 各学习基线训练预算、早停和 checkpoint 选择未统一 | 高 |
| 参数量 | C0–C2 生成模型计划相同 | 路由编码器、重排器、反思模型和辅助模块参数未完整计入 | 高 |
| 预训练 | 生成模型计划冻结一致 | Self-RAG/FLARE/RouteLLM 式基线可能使用不同预训练或专用 checkpoint | 高 |
| 超参数调优 | 禁止测试集调参 | 搜索空间、试验次数、选择指标和计算预算没有预注册 | 高 |
| 随机种子 | 文档要求配对种子 | 当前 `seed=42` 主要控制任务顺序，没有传入生成后端，也没有多训练种子 | 高 |
| 评价指标 | 指标体系较完整 | 正式人工标签尚无；不同 coverage 下直接比风险或资源可能误导 | 高 |

因此，现阶段 Windows smoke 结果只能证明程序可运行，不能作为基线优劣证据。

## 2. 数据划分

### 已经公平的部分

- 所有方法使用同一查询集合、知识库和协议版本；
- 计划按 `source_group_id` 分组，能防止同一事件、模板或改写跨集合；
- 风险阈值计划只在独立校准集确定；
- Gold Evidence 只用于 R2 上限参考，不提供给可部署方法。

### 潜在不公平

1. **训练、调参和校准的角色还没有完全分开。**  
   当前正式脚本使用 `train` 训练风险模型、`cal_op` 选择阈值，但没有明确使用
   `valid` 做早停、模型选择和普通超参数调优。如果 PROPOSED 在 `cal_op` 上选择
   模型结构，而基线只用它选阈值，PROPOSED 会额外接触校准信息。

2. **没有锁定所有方法共用的样本 ID 清单。**  
   仅写“相同划分”还不够，应保存每个 split 的查询 ID、`source_group_id`、
   协议版本和文件 SHA-256。任何方法因解析失败而静默跳过样本，都会破坏配对公平。

3. **单次划分可能偶然有利于某一方法。**  
   当前划分算法固定 seed 42。主结论可使用一个预注册划分，但至少应增加若干
   group-level 重划分作为稳健性实验，报告风险约束越界频率。

4. **F0 的“所有可回答查询”表述不公平。**  
   F0–F2 必须面对全部测试查询，包括 gold 应回退查询。不能预先排除“不可回答”
   查询，否则固定生成基线会避开最危险样本。

5. **知识库覆盖可能泄露测试难度。**  
   若根据测试查询补录协议、同义词或 BM25 规则，会使检索基线受益。知识库、
   分块、停用词、同义词表和索引参数必须在测试前冻结。

### 修正要求

- 固定六类数据角色：`train`、`valid`、`cal_op`、`cal_ch`、`test_op`、
  `test_ch`；
- `valid` 只负责早停、架构和普通超参数选择；
- `cal_op` 只负责安全阈值，不能选择特征、模型或检索参数；
- `cal_ch` 只检查偏移，不能重新选阈值；
- 测试集运行失败、超时和 OOM 仍保留在分母中；
- 为每个 split 输出 ID 清单、统计摘要和 SHA-256。

## 3. 训练轮数与优化预算

### 潜在不公平

当前代码中的逻辑风险模型固定训练 1200 次迭代，但 A1、A3、S1、S2、S3、S4 和
PROPOSED 尚未建立统一训练协议。简单规定“相同 epoch”也不一定公平，因为不同
方法每个 epoch 的样本数、负样本数或配置展开数可能不同。

可能出现的偏差包括：

- PROPOSED 训练更久或使用更多配置级标签；
- 某基线没有早停而过拟合，PROPOSED 使用最优验证 checkpoint；
- 只为 PROPOSED 重复训练和选择最佳 seed；
- 为不同方法使用不同类别采样或正负权重，却没有报告；
- 把超参数搜索产生的多次训练不计入 PROPOSED 的训练预算。

### 公平规则

- 对匹配架构方法统一 optimizer、batch size、最大 optimizer steps、学习率调度、
  早停 patience 和 checkpoint 选择指标；
- 比较总样本曝光数和 optimizer steps，而不只比较 epoch；
- 所有方法使用相同的最大训练预算和相同早停规则；
- 每个方法对每个预注册 seed 只保留验证规则自动选出的 checkpoint，不能人工挑
  最好测试结果；
- 原论文方法若必须采用其官方训练配方，应作为“原配方复现”单列，不能与
  matched-capacity 消融混为一组。

## 4. 参数量与计算容量

### 已经公平的部分

C0–C2 使用相同生成模型、量化、上下文长度和解码设置，这是端到端配置比较的正确
基础。

### 潜在不公平

- “生成模型相同”不等于“系统容量相同”；查询编码器、交叉编码器、重排器、
  自反思模型、风险头和设备状态编码器都应计入；
- A1 只说“相同编码器或相同参数预算”，但 A3、S1、S2、S3 和 PROPOSED 没有
  完整参数锁定；
- A2 若调用生成模型额外产生反思 token，其额外计算不是免费参数；
- C2 的重排、多步检索和验证器若使用额外模型，应报告其参数和内存；
- T0/T1 不需要参数量相等，但其人工规则开发预算应报告，避免把大量人工优化视为
  零成本。

### 公平规则

参数公平应分两类处理：

1. **机制消融和匹配架构比较**：A1、S1、S2、S3、AB 系列与 PROPOSED 使用同一
   编码器、隐藏维度、预测头和训练预算，只改变声明的特征或校准模块。
2. **真实系统基线**：T0、T1、官方论文方法和固定配置允许参数量不同，但必须报告
   总参数、可训练参数、峰值内存、每查询计算和辅助模型，不得只报告主生成模型。

建议表格同时列出：

- 生成模型参数；
- 检索/嵌入模型参数；
- 重排/验证模型参数；
- 路由器总参数和可训练参数；
- 模型文件总大小；
- 峰值 RSS；
- 路由器端到端额外时延和能耗。

## 5. 预训练与外部信息

### 潜在不公平

1. Self-RAG、FLARE 和 RouteLLM 式方法可能依赖专用预训练、偏好数据或模型内部
   token 置信度，而 PROPOSED 使用普通本地模型。若直接使用不同 checkpoint，
   结果同时反映预训练差异和路由差异。
2. 查询编码器、稠密检索器和重排器可能在不同规模数据上预训练。
3. 基础模型可能在预训练阶段见过公开灾害问答或协议，C0 会因此获得隐性检索优势。
4. 只允许 PROPOSED 使用额外协议元数据、冲突标注或设备运行历史，也属于额外训练
   信息，必须在比较问题中明确。

### 修正要求

- 建立两条结果轨道：
  - `Matched implementation`：同生成模型、同编码器和同训练数据，只比较机制；
  - `Official/faithful implementation`：保留官方 checkpoint 和训练配方，报告其
    额外数据与参数，作为生态系统参考。
- 对无法复现原训练的 A2 明确命名为 `FLARE-inspired` 或
  `Self-RAG-inspired`；
- 记录所有模型的仓库、revision、许可证、量化、SHA-256 和已知训练数据；
- 对公开测试集增加污染敏感性分析，不能把 C0 对熟悉题目的记忆当作路由能力。

## 6. 超参数调优

### 潜在不公平

当前方案禁止测试集调参，但尚未定义：

- 每个方法允许多少次 trial；
- 搜索空间是否同等宽；
- 选择 checkpoint 的主目标；
- top-k、chunk size、重排深度、阈值、类别权重和正则强度在哪里确定；
- 计算预算耗尽时如何处理失败 trial。

这会产生“只精调 PROPOSED、基线使用默认参数”的典型不公平。

另外，下列比较需要特殊处理：

- A4 若按固定 coverage 调阈值，而 PROPOSED 按固定 \(\alpha,\delta\)，两者目标
  不一致；
- S2 使用经验阈值、S3 使用温度缩放、PROPOSED 使用风险上界时，应同时报告
  相同目标风险下的 coverage，以及相同 coverage 下的实际风险；
- C1 的 top-k=5、C2 的 top-k=12 属于待调参数，不能在测试观察后固定；
- T1 人工规则的条数和阈值也属于超参数，必须只用 train/valid 冻结。

### 公平规则

- 为所有学习方法预注册相同 trial 数或相同总训练 GPU/CPU 小时；
- 匹配方法使用同一搜索算法；
- 搜索空间可因方法结构不同而不同，但宽度、依据和预算必须公开；
- 用统一验证目标选择普通超参数，例如：
  `满足 valid 风险门槛后最大化行动完整率，再最小化资源`；
- 校准集只选安全阈值，不回头修改模型；
- 同时报 fixed-risk、matched-coverage 和完整 Pareto 曲线。

## 7. 随机种子

### 当前实现风险

当前 `radxa.experiment.json` 的 seed 42 用于打乱穷举任务顺序，但：

- 没有传给 `llama-server` 的生成请求；
- 结果行没有完整记录训练 seed、生成 seed、划分 seed 和顺序 seed；
- 风险模型训练当前是确定性迭代，没有多 seed 不确定性；
- 只有 3 次 `repetition`，但 repetition 不等于独立训练 seed；
- 随机路由 R0 的随机流尚未实现；
- 热态会话的顺序平衡尚未真正执行拉丁方。

因此，文档中的“相同或配对随机种子”尚未落实到代码级。

### 修正要求

至少区分并记录：

| seed | 用途 |
| --- | --- |
| `split_seed` | group-level 数据划分 |
| `train_seed` | 参数初始化、batch 顺序和负采样 |
| `generation_seed` | C0–C2 解码采样 |
| `route_seed` | R0 随机路由 |
| `order_seed` | 配置、查询和设备会话顺序 |
| `bootstrap_seed` | 区间与重采样统计 |

确认性实验建议至少 5 个训练 seed；若训练成本过高，最低 3 个，但需要明确局限。
每个 query×configuration×generation seed 应配对。温度为 0 时仍应记录 seed 和
后端确定性设置，因为不同推理后端可能并非位级确定。

## 8. 评价指标

### 已经合理的部分

- L3 严重失效、risk@coverage、行动完整率、焦耳/查询和 P95 覆盖了安全、服务
  质量和资源三条主轴；
- 计划使用配对统计、区间和 Holm–Bonferroni；
- 拒答、超时、OOM 和人工升级计入结果；
- 只有满足安全约束的方法参与资源最优排名。

### 潜在不公平

1. **当前自动评价只能用于 smoke。**  
   现有代码明确标记为 `smoke_heuristic_not_publication_grade`。字符串匹配不能替代
   盲法专家 L3、安全规则和行动完整率评价。

2. **不同 coverage 下直接比较风险不公平。**  
   更保守的方法可以通过大量 C3 获得更低风险。必须同时报告总体 coverage、
   answered-only risk、服务层风险和 matched-coverage 比较。

3. **不同 coverage 下直接比较平均能耗也可能不公平。**  
   大量拒答天然更省电。应报告：
   - 每到达查询能耗；
   - 每已回答查询能耗；
   - 每安全且完整回答能耗；
   - coverage—risk—energy 三维前沿。

4. **C3 不应被当作普通高资源配置。**  
   S4 将 C2/C3 合并为“高资源路径”，但当前 C3 是低计算的安全回退。C3 的本质是
   服务决策而不是更强生成配置，应分别报告 fallback，不以“高资源路径”概括。

5. **上限参考不能参与普通显著性排名。**  
   R2、R3、R4使用 gold 或事后信息，只能报告 gap/regret，不能写成部署方法优于或
   劣于 oracle 的普通竞赛式结论。

6. **人工评价必须真正盲法。**  
   标注界面不得显示方法名、配置名、时延或能耗；同一查询的答案顺序应随机化。
   应报告双标比例、一致性和裁决规则。

### 推荐主结果口径

- 主要安全结果：L3 风险上界、风险约束越界频率；
- 主要服务结果：总服务 coverage 和必要行动完整率；
- 主要资源结果：焦耳/到达查询、P95 端到端时延；
- 必须伴随：matched-coverage risk、每安全完整回答能耗、fallback rate；
- C0–C2 使用相同人工评分 rubric，C3 单独评价“回退是否恰当”；
- 所有置信区间以查询组或设备会话为重采样单位，不能把同一查询的重复运行当作
  独立样本。

## 9. 基线特有的不公平风险

| 基线 | 潜在问题 | 公平修正 |
| --- | --- | --- |
| T0 | 模板和规则可能经过大量人工测试集式优化 | 只用 train/valid 编写，报告规则数、开发工时和冻结版本 |
| T1 | 人工规则可能使用 PROPOSED 不可见的领域信息 | 限制为同一决策前变量，公开优先级和冲突处理 |
| F0–F2 | 可能只在“可回答查询”上运行 | 必须运行全部查询，失败和错误回答保留在分母 |
| A1/A3 | 可能使用更小编码器、较少训练标签 | 使用 matched-capacity 版本，并另列官方版本 |
| A2 | 专用反思 checkpoint 或额外生成 token | 分开报告预训练差异、额外 token、时延和能耗 |
| A4 | 按 coverage 调阈值而 PROPOSED 按风险调阈值 | 同时做 fixed-risk 与 matched-coverage 比较 |
| S1/S2/S3 | 名义相同结构但隐藏维度或训练预算不同 | 复用同一代码路径，仅切换特征/校准模块 |
| S4 | 将 C3 称为高资源路径 | 将“资源升级”和“服务回退”分开建模 |
| S5 | C2 计算总在拒答前发生 | 计入完整 C2+拒答成本，不与提前回退混淆 |
| R2/R3/R4 | 使用 gold/事后信息 | 只作上限和 regret 参考 |

## 10. 当前代码与纸面方案的关键偏差

这些偏差不修正时，不能把当前实现称为完整 PROPOSED：

1. 当前 `LogisticRiskPredictor` 只使用查询风险等级、长度、信息不足等 query
   features，没有实现知识状态和实时设备状态输入；
2. 当前路由使用离线资源画像，不是论文定义的实时设备状态联合预测；
3. 当前 C1 是纯 BM25，尚不是文档中的单步向量/混合 RAG；
4. 当前 C2 是 BM25 候选加协议元数据重排，尚无真正混合检索、多步检索和规则验证；
5. T0、T1、A1–A4、S1–S5 和大部分消融尚未实现为可运行代码；
6. 生成 seed 尚未传递给 `llama-server`；
7. 正式 Radxa 配置中的功率路径尚为空，无法形成正式焦耳/查询；
8. 真实协议、正式查询集、正式人工判定和 GGUF 模型尚未接入。

当前 smoke 结果可以作为工程验收，不得进入论文主结果表。

## 11. 建议锁定的公平实验协议

在运行测试集前生成并冻结一张 `fairness_lock.json`，至少包含：

```json
{
  "dataset_manifest_sha256": "TO_BE_FILLED",
  "knowledge_base_sha256": "TO_BE_FILLED",
  "generator_model_sha256": "TO_BE_FILLED",
  "split_seed": 42,
  "train_seeds": [11, 23, 37, 51, 71],
  "generation_seeds": [101, 103, 107],
  "order_seeds": [211, 223, 227],
  "alpha": 0.05,
  "delta": 0.05,
  "max_output_tokens": 512,
  "hyperparameter_trials_per_method": 30,
  "checkpoint_metric": "valid_safe_action_completeness_then_energy",
  "test_tuning_forbidden": true
}
```

推荐执行顺序：

1. 冻结数据、知识库、模型和评价 rubric；
2. 实现所有确认性基线的统一接口；
3. 在 train 上训练，在 valid 上早停和调普通超参数；
4. 在同一 cal_op 上为各安全方法独立校准，但使用相同
   \(\alpha,\delta\) 和风险标签；
5. 冻结全部模型与阈值；
6. 对所有测试查询穷举 C0–C3，形成配对潜在结果矩阵；
7. 对静态路由做矩阵重放，对热态设备策略做真实连续运行；
8. 盲法人工评分；
9. 同时报告 fixed-risk、matched-coverage、系统级真实资源和 oracle gap；
10. 任何失败、超时、OOM 或缺失标签不得静默删除。

## 12. 最终结论

现有纸面对照不是“明显不公平”，但存在多项足以改变结论的未锁定自由度。最需要
优先修正的是：

1. 分离 valid 与 calibration 的用途；
2. 为匹配架构基线统一训练和调参预算；
3. 完整登记参数量、预训练和外部数据；
4. 实现多训练 seed、配对生成 seed 和顺序平衡；
5. 在 matched coverage 下比较安全和资源；
6. 将当前 query-only 简化实现与真正 query+corpus+device PROPOSED 区分；
7. 在正式数据、人工标签和 Radxa 物理能耗就绪前，不将 smoke 结果作为论文证据。
