# 新手实验执行流程教程 v1.0

本教程面向第一次运行本项目的用户。按顺序执行：Windows 验证 -> 复制到 Radxa -> Radxa smoke -> 小规模先导 -> 训练和校准 -> 最终测试。

> 当前状态
>
> - 当前 400 条数据是 `development_gold`，只能用于开发验证，不是最终确认性测试集。
> - 2026-07-29 已在 Radxa ZERO 3W 上完成 ARM64 `llama-server` 构建、模型加载、
>   `/health` 和 `/v1/chat/completions` 实测；运行时仍依赖构建目录中的共享库。
> - 当前 GGUF 通过 Chat API 可以生成，但裸 `/completion` 立即返回 EOS；
>   项目 `LlamaServerGenerator` 尚未适配 Chat API，因此真实 LLM 先导仍未通过。
> - ESP32-S3 当前损坏、替换件在途，物理功率路径和 INA226 三点校准尚未完成。
> - Windows/Radxa smoke 只证明工程链路可运行，不能直接作为论文结论。
> - 正式结果必须有输出级人工双审、真实功率积分和冻结后的 `test_op/test_ch` 单次最终运行。

## 0. 2026-07-29 首次实机验证结论

这次实机运行暴露了计划阶段无法确认的四个差异：

1. `llama-server` 的 C++ 主体可以增量续编；中断后不应删除
   `third_party/llama.cpp-b9627/build-e1-release`。
2. Hugging Face UI 下载超时不是核心编译失败。关闭在线 UI 后，旧 UI 缓存还可能
   因缺少 `loading.html` 与新版嵌入器不兼容。
3. 当前 `bin/llama-server` 只有约16 KiB是正常的，它是动态链接入口；所需
   `libllama-server-impl.so`、`libllama-common.so`、`libllama.so` 和
   `libggml*.so` 仍在构建目录中。
4. `radxa.smoke.json` 使用 `extractive` 后端，不会调用本地 GGUF。服务健康、
   smoke 成功和真实模型生成是三个不同门禁，必须分别验证。

完整证据和命令见
`docs/Radxa_ZERO3W首次实机运行记录_v1.0.md`。

## 5. 数据预处理

处理对象有两类：

1. 查询 JSONL：字段、长度、重复、`source_group_id` 分组泄漏和数据划分。
2. 运行 JSONL：状态、时延、内存、温度、功率和异常记录。

已有 400 条数据已经处理过，且是 `development_gold`；不要覆盖式重跑或改名为最终测试集。新建原始查询集时：

```powershell

```

`output-directory` 必须使用新版本目录；`fail-on-quarantine` 会在发现隔离记录时停止，不能静默删除。

开发运行结果可以处理为：


```powershell

```

没有物理功率时，`energy_j` 必须是 `null`，不能用时延或 token 数代替。

### 9.1 构建中断和 UI 下载超时

构建中断后直接重新运行同一脚本，CMake 会复用已完成的对象文件。不要清空构建
目录。离线构建时先写入 CMake 缓存：

```bash
SOURCE_DIR=/home/radxa/sci-exp/third_party/llama.cpp-b9627
BUILD_DIR="$SOURCE_DIR/build-e1-release"

cmake -S "$SOURCE_DIR" -B "$BUILD_DIR" \
  -DCMAKE_BUILD_TYPE=Release \
  -DGGML_NATIVE=ON \
  -DGGML_OPENMP=ON \
  -DLLAMA_CURL=OFF \
  -DLLAMA_BUILD_TESTS=OFF \
  -DLLAMA_BUILD_UI=OFF \
  -DLLAMA_USE_PREBUILT_UI=OFF
```

如果旧 UI 缓存报 `missing required asset(s): loading.html`，源码中已有该文件，
可补入缓存后续编：

```bash
cp "$SOURCE_DIR/tools/ui/static/loading.html" \
  "$BUILD_DIR/tools/ui/dist/loading.html"
bash "scripts/构建并锁定ARM64_llama_server.sh"
```

`embedding stale assets` 是回退警告；只有出现
`[100%] Built target llama-server`、版本记录和 SHA-256 后才算成功。

### 9.2 共享库和 HTTPS 边界

实测 `ldd bin/llama-server` 会从
`third_party/llama.cpp-b9627/build-e1-release/bin` 加载共享库。因此：

- 不要删除或移动 `build-e1-release`；
- 只复制16 KiB的 `bin/llama-server` 不能形成独立可搬运运行时；
- 当前设备未找到 OpenSSL，`llama-server` 只提供 HTTP，不提供自身 HTTPS；
- 正式冻结前如需可搬运包，应显式收集共享库并重新执行 `ldd` 验证。

手动等价命令：

```bash
/home/radxa/sci-exp/bin/llama-server --model /home/radxa/sci-exp/models/qwen1_5-0_5b-chat-q4_k_m.gguf --host 127.0.0.1 --port 8080 --ctx-size 4096 --threads "$(nproc)"
```

另开 SSH 窗口测试 `curl http://127.0.0.1:8080/health`。健康检查失败时不要继续。

第一个窗口前台运行服务器时，第二个窗口只运行 `curl` 和 Python 实验命令，
不要再次启动服务器。也可使用后台方式只保留一个窗口：

```bash
nohup bash scripts/start_llama_server.sh \
  > results/llama-server.log 2>&1 &
echo $! > results/llama-server.pid
```

停止后台服务器：

```bash
kill "$(cat results/llama-server.pid)"
```

### 9.3 模型接口必须单独验证

当前 Qwen Chat GGUF 对裸文本接口的实测结果是空正文和单个 EOS，因此下面的
测试**不通过**：

```bash
curl http://127.0.0.1:8080/completion \
  -H "Content-Type: application/json" \
  -d '{"prompt":"请用一句话说明发生地震时首先应该做什么。","n_predict":64,"temperature":0}'
```

Chat API 可以生成正文：

```bash
curl http://127.0.0.1:8080/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{
    "model":"qwen1.5-0.5b-chat",
    "messages":[
      {"role":"system","content":"你是一个简洁、可靠的应急助手。"},
      {"role":"user","content":"请用一句话说明发生地震时首先应该做什么。"}
    ],
    "max_tokens":64,
    "temperature":0
  }'
```

接口返回文字只证明推理链路可用，不代表答案安全或模型达到正式质量门槛。首次
实测回答把“拨打110”作为地震首要行动，必须在 RAG 证据约束和双人盲审中判定，
不能直接接受为正确答案。

当前 `src/sci_exp/generation.py` 仍发送裸 `/completion` payload，并读取顶层
`content`；`configs/radxa.experiment.json` 也仍指向 `/completion`。在两者同时
适配 `/v1/chat/completions` 的 `messages` 和
`choices[0].message.content` 前，不得启动真实 LLM 全量运行。

## 14. 常见问题

- **`No module named sci_exp`**：设置 Windows 的 `$env:PYTHONPATH` 或 Radxa 的 `export PYTHONPATH`。
- **`errors` 非空**：停止，检查 JSONL、证据 ID 和 `source_group_id` 分组泄漏。
- **服务启动失败**：执行 `file bin/llama-server` 和 `ldd bin/llama-server`，确认是 ARM64 可执行文件。
- **Hugging Face UI下载超时**：关闭`LLAMA_BUILD_UI`和
  `LLAMA_USE_PREBUILT_UI`后增量续编；这不是核心模型库编译失败。
- **UI缺少`loading.html`**：从`tools/ui/static/loading.html`复制到构建缓存
  `tools/ui/dist/loading.html`后续编，不要删除整个构建目录。
- **`/completion`返回空字符串**：Chat GGUF没有套用聊天模板；先用
  `/v1/chat/completions`验证，并同时修改生成请求和响应解析。
- **smoke成功但模型未生成**：`radxa.smoke.json`使用extractive后端，这是预期
  行为；另做真实LLM先导。
- **dense 加载失败**：检查 BGE 目录和 ARM64 torch 兼容性，不要把 hashing 结果冒充 dense。
- **没有功率读数或ESP32损坏**：可以继续代码、数据和无能耗开发诊断；正式资源
  画像、能耗路由、主实验和最终测试必须暂停。
- **训练/校准停住**：通常是在等待人工 `train_adjudication.jsonl` 或 `calibration_adjudication.jsonl`，完成双审后继续。

## 15. 正式论文结果门槛

只有同时满足以下条件才能把结果写进论文：

1. 数据分区冻结且无 group leakage。
2. 训练、校准、测试严格隔离。
3. Radxa ARM64 runtime、模型哈希、线程数和设备信息有记录。
4. 输出完成盲法双审和冲突仲裁。
5. `energy_j` 来自校准后的物理功率积分。
