# 实验记录与智能体交接规则 v1.0

## 目的

本规则解决两个问题：避免智能体重新扫描仓库后重复从E0开始；避免“做过一次”被误写成
“已满足正式门槛”。

## 权威顺序

1. `docs/实验状态总览_v1.0.yaml`：当前进度、完成项、阻断项和下一动作。
2. `docs/E0-E8实验设计与执行协议_v1.0.md`：冻结的实验要求和停止规则。
3. `docs/实验日志/`与`results/`：实验经过和分析证据。
4. `data/raw/`：不可反向修改的原始证据。
5. README、历史任务清单和旧聊天：只作背景，不能覆盖上述状态。

## 状态判定

- **完成门槛**：已经满足冻结要求，并有可定位、可核验的原始证据和分析报告。
- **部分完成**：部分门槛有证据，但阶段总门槛未通过。
- **等待硬件**：后续真实测量依赖在途硬件。
- **正式阻断**：可以继续准备，但不能产出或宣称论文级结果。
- **dry-run**：只检验代码和流程，`formal_evidence`必须为`false`。

“已有输出文件”不等于完成；“程序gate为true”也不能替代冻结协议中未编码的要求。

## 智能体开工规则

每个新智能体必须先回答以下问题，再运行命令：

1. 当前阶段状态是什么？
2. 哪些门槛已完成且不应重跑？
3. 本任务是否依赖E0正式通过？
4. 本次输出是正式证据还是dry-run？
5. 会不会覆盖已有session、run ID或原始文件？

若账本与证据冲突，必须先登记异常，不得自行选择更乐观的结论。

## 实验结束后的最小记录

每次真实实验至少记录：

- `exp_id`、session、run ID和阶段；
- 日期、时区、操作者；
- 设备型号/编号、固件版本、接线、参考仪器及准确度依据；
- 完整执行命令和环境变量；
- 开始/结束时间、持续时间、目标和实际条件；
- 原始文件路径、字节数、记录数、SHA-256；
- 分析脚本、参数、报告路径和接受门槛；
- 结论、异常、偏离协议及下一动作。

原始文件不得覆盖。重复实验使用新的session和run ID，并在日志中说明与旧运行的关系。

## 大型原始数据与Git

高频JSONL不适合直接进入代码Git仓库。标准做法是：

1. 完整raw压缩保存到Git之外的实验数据目录、对象存储或研究数据仓库；
2. Git提交分析报告、manifest、schema和小型首尾摘录；
3. manifest记录原始文件名、session、样本数、字节数、SHA-256、压缩格式和外部位置；
4. 摘录使用`*.excerpt.jsonl`，并明确`formal_evidence: false`与`complete_raw: false`；
5. 不得在完整原始文件名下删除中段，因为后续程序和智能体会误认为它仍是完整raw。

若完整raw已经被主动删除，记录`retention_status: intentional_excerpt`。摘录不需要被误判为
未知损坏，但也不能用于重算长时连续性指标；需要正式复核时，应找回外部副本或重采。

## 当前并行工作边界

E0未正式通过时，可以继续：代码适配、单元测试、数据治理、标注、模型/运行时审计、
三点校准脚本准备和明确标为非正式的dry-run。

不能提前计入正式结果：E1的C0/C1/C2穷举、单查询能耗、节能率、能耗预测、Router净节能、
Gold Test和任何依赖`external_meter_valid=true`的结论。

## 更新规则

- 只更新事实发生变化的字段，不删除历史日志。
- 阶段通过时写入通过报告路径和SHA-256，再将`formal_pass`改为`true`。
- 设备、固件、分流电阻、接线或参考仪器改变时，旧校准不自动继承。
- 证据缺失、截断或哈希不一致时，登记到`docs/实验日志/异常记录.md`。
